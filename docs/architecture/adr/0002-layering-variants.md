# ADR-0002：跨语言代码分层——双变体可选

> status: accepted · date: 2026-11-12 · owner: ZnLuAr

## 背景

多语言项目若各用各的目录习惯，人和 AI 每换一种语言就要重建一次导航模型；用户 ai-work-config 的 `core/workflow.md` §3 读代码固定沿「入口 → use case → 领域规则 → 持久化/外部系统 → 测试」的链条。本模板曾两度评估单一方案：先采用四层 `entry / service / domain / infra`（端口为架构前提），后考虑改为三层式 `entry / logic / model / infra`（接口按需引入）。两种取舍各有真实代价——四层的概念命名（domain / infra / 端口）对使用者存在持续的语义税，day-1 强制接口对多数小项目过重；三层式规则强度低，业务规则复杂多变时约束力不足。评估未收敛，决定不赌方向。

## 决策

每种语言 scaffold 提供**两种分层变体**，实例化时由 `--arch` 选择，不选的那套不进入项目：

| | `--arch cls`（classic，默认） | `--arch hex`（hexagonal） |
|---|---|---|
| 目录 | `entry / logic / model / infra` | `entry / service / domain / infra` |
| 铁律 | model 零 IO、不 import 任何层 | `entry → service → domain`；`infra → domain`；其余方向禁止 |
| 接口角色 | 测试与替换的**按需工具**：logic 默认直接用 infra 类型，要替身测试或预知换实现时才抽 model 接口（渐进条款） | **架构前提**：所有外部依赖经端口，domain 定义、infra 实现、依赖倒置 |
| 命名来源 | 传统三层（handler/logic/model/db）习惯，技术角色自解释 | 六边形架构行业词汇，与 DDD 文献对齐 |
| 适配场景 | 小工具、CRUD 密集、技术栈统一 | 业务规则复杂多变、依赖需长期可替换 |

全称 `classic` / `hexagonal` 作为 `--arch` 的兼容别名保留。

**共性规则**（两变体相同）：组装只在 entry（infra 实例的构造与注入不进 logic/service）；测试镜像分层（unit 覆盖规则与业务层，integration 覆盖入口与外部系统）；`scaffold/<lang>/variants/<arch>/` 中同一 Greeter 示例同构实现，作为活文档。

**默认值取 cls**：模板的主要实例化场景是小项目，痛点在过度设计；复杂项目显式指定 `hex`。

## 备选方案

- **只做四层**（本 ADR 前身）：概念命名语义税与 day-1 端口强制对小项目过重，被否。
- **只做三层式**：丢失强约束与依赖倒置能力，且没有成文演进路径，被否。
- **单套 scaffold + init 时机械改写**（重命名目录与替换措辞）：改写脚本成为隐藏的代码生成器，措辞替换产出的缝合怪难以维护，被否。

## 后果

**正面**

- 决策从一次性全局赌注降为每次实例化的局部选择；将来若某变体占比压倒性（如 90%），删除另一变体比现在赌错再补建容易；
- 两套规范在同一模板内互为参照，评估永久化——用哪个不再靠想象，靠实际用脚投票。

**负面与代价**

- 维护面扩大：分层骨架 ×8（4 语言 × 2 变体）、standards 分层小节双写、冒烟用例 ×8（变体间工具链配置共享，重复受控于 `variants/` 结构）；
- 工作目录下将同时存在两种分层的项目，人与 AI 需按各项目 CLAUDE.md 的语言规则段识别（已由生成器自动标注）；
- 两变体示例代码同构（都注入 + fake），差异在规则强度与文档——「对比」由规范承载而非示例形态。
